## 기존 모놀리식 코드의 의존 관계 분석
헥사고날 전환 직전 코드(`5ec09ed` — 주문·재고 예약·목업 결제·예약 만료 스케줄러까지 구현한 시점)를 기준으로 의존 관계를 분석한다

### 구조
기술 계층형 구조였다

```
domain
├── base/BaseEntity
├── order    — Order, OrderItem, controller, service, repository, dto, enums, scheduler
├── product  — Product, controller, service, repository, dto
├── stock    — Stock, StockReservation, controller, service, repository, dto, enums
└── payment  — controller, service, dto, enums
common/exception — 공통 코드와 도메인별 에러 코드(주문·상품·재고·예약)가 한곳에
```

+ 도메인 단위 패키지는 있었지만 계층의 경계와 컨텍스트의 경계가 코드에 없었다
    - 섹션 1 에서 재고는 상품 컨텍스트가 소유한다고 정했지만 `stock` 이 별도 패키지로 나뉘어 있었다
    - 도메인별 에러 코드가 모두 `common/exception` 에 모여 있었다

### 컨텍스트 사이 의존
|호출하는 쪽|호출되는 쪽|방식|
|---|---|---|
|주문 `OrderService`|상품 `ProductRepository`, `Product`|상품 저장소를 직접 조회해 엔티티를 받는다|
|주문 `OrderService`|재고 `StockRepository`, `Stock`, `StockReservationService`|재고 저장소를 직접 조회하고 예약 서비스를 직접 호출한다|
|주문 `Order`|재고 `StockReservation`|JPA 양방향 연관 (`@OneToMany`), 주문이 예약을 직접 확정·해제한다|
|재고 `StockReservation`, `StockReservationService`|주문 `Order`|JPA 연관 (`@ManyToOne`), 주문 엔티티를 인자로 받는다|
|결제 `PaymentService`|주문 `OrderService`|주문 서비스 구현체를 직접 호출한다|

+ 주문 ↔ 재고 예약이 양방향으로 묶여 순환 의존이었다
    - `Order.cancel()` 이 `StockReservation` 을 직접 해제하고, 예약은 `Order` 엔티티를 들고 있었다
    - 섹션 1 에서 "상품은 주문의 존재를 몰라야 한다"고 정했지만 코드는 반대로 되어 있었다
    - 컨텍스트를 나누려면 객체 그래프를 통째로 뜯어야 하는 구조였다
+ 주문이 상품의 저장소와 엔티티를 직접 만졌다
    - 상품 컨텍스트의 내부(엔티티 필드, 저장소 메서드)가 바뀌면 주문도 함께 바뀐다
    - 다른 컨텍스트로 들어가는 정해진 입구가 없었다
+ 결제가 주문 서비스의 구현체에 의존했다
    - 결제가 알아야 할 것은 "결과를 알린다"뿐인데, 주문의 어떤 메서드를 불러야 하는지까지 알고 있었다

### 계층 사이 의존
|위치|의존|문제|
|---|---|---|
|`*/repository`|Spring Data `JpaRepository` 상속|저장소 계약이 JPA 에 묶이고, `Pageable` 이 서비스까지 올라온다|
|`OrderService.createOrder` · `ProductService.register` · `update`|요청 DTO (`CreateOrderRequest`, `ProductRegisterRequest`)|서비스가 웹 요청 형식에 의존한다 (안쪽이 바깥쪽을 안다)|
|`ProductService`|`jakarta.transaction.Transactional`|읽기 전용 트랜잭션(`readOnly`)을 쓸 수 없다|
|`Product`|클래스 레벨 `@Setter`|어디서든 필드를 하나씩 바꿀 수 있다|

### 외부 기술 의존
|위치|외부 기술|
|---|---|
|도메인 모델 (`Order`, `OrderItem`, `Product`, `Stock`, `StockReservation`) · `BaseEntity`|JPA, Spring Data Auditing|
|저장소|Spring Data JPA|
|서비스|Spring (`@Service`, `@Transactional`, `@Value`), Spring Data (`PageRequest`), Bean Validation|
|에러 코드 (`BaseErrorCode` 와 도메인별 코드)|Spring Web `HttpStatus`|

### 정리
+ 끊어야 할 것
    - 주문 ↔ 재고 예약의 양방향 연관 (순환 의존)
+ 감춰야 할 것
    - 주문이 상품·재고를 부르는 지점, 결제가 주문을 부르는 지점 → 부르는 쪽의 출력 포트
    - 컨텍스트로 들어오는 입구 → 입력 포트(유스케이스)
+ 뒤집어야 할 것
    - 서비스가 웹 요청 DTO 와 Spring Data 에 기대는 방향 → 커맨드, 일반 인터페이스로 된 저장소 포트

이 분석을 바탕으로 [Domain / Application / Adapter 영역으로 역할을 분리](Domain-Application-Adapter-영역으로-역할-분리.md)했다
