## 핵심 도메인이 외부 기술에 직접 의존하지 않도록 구조 개선

### 개선한 것
|전|후|
|---|---|
|저장소가 `JpaRepository` 를 상속하고, `Pageable` 이 서비스까지 올라온다|저장소 포트는 일반 인터페이스이고 건수(`limit`)만 받는다. Spring Data 는 `adapter/out/persistence` 에만 있다|
|서비스가 웹 요청 DTO 를 받는다|서비스는 커맨드를 받는다. 요청 → 커맨드 변환은 `adapter/in/web` 이 맡는다|
|주문이 상품 엔티티와 저장소를 직접 쓴다|주문은 `ProductPort` · `StockPort` 로만 부르고 상품 엔티티를 모른다|
|주문 ↔ 재고 예약이 JPA 양방향 연관으로 묶여 있다|재고 예약은 주문 ID 만 가진다|
|결제가 주문 서비스 구현체를 부른다|결제는 `OrderPort` 로 결과만 알린다|
|`Product` 에 클래스 레벨 `@Setter`|`update()` 로만 바뀐다|

+ 포트와 서비스는 JPA·Spring Data·웹 요청 형식을 모른다 (포트의 외부 기술 import 0건)
+ 영속성·웹·다른 컨텍스트 호출이 바뀌면 어댑터만 바뀐다

### 지금 영역별 외부 기술
|영역|외부 기술 import|
|---|---|
|**domain**|**`jakarta.persistence` (JPA), `org.springframework.http` (Spring Web)**|
|application/port/in · out|없음|
|application/service|Spring (`@Service`, `@Transactional`, `@Value`)|
|adapter/in|Spring Web, Bean Validation, Swagger, Spring 스케줄링|
|adapter/out|Spring Data JPA|

domain 에 남은 두 의존은 아래와 같이 판단했다

### 1. 도메인 모델의 JPA 애너테이션 — 의도한 트레이드오프
+ 남은 것
    - `Order`, `OrderItem`, `Product`, `Stock`, `StockReservation` 이 `@Entity` · `@Column` 등 JPA 애너테이션을 직접 가진다
    - 모두 상속하는 `BaseEntity` 는 Spring Data Auditing(`@CreatedDate`, `AuditingEntityListener`)도 쓴다
    - `Stock` 의 `@Version`(낙관적 락), `StockReservation` → `Stock` 의 `@ManyToOne` 도 영속성 개념이다
+ 남긴 이유
    - 섹션 2 의 목적은 포트·어댑터로 경계를 드러내는 것이고, 그 경계는 코드로 검증된다
        + 포트의 외부 기술 import 0건, 다른 컨텍스트를 아는 파일은 출력 어댑터 3개뿐
    - 애너테이션은 매핑 정보(메타데이터)일 뿐이고, 도메인 로직이 JPA API 를 부르지는 않는다
        + 상태 전이·금액 계산·예약 규칙은 DB 없이 단위 테스트로 검증한다
    - 분리하면 애그리거트마다 JPA 엔티티와 매퍼가 생기고, 변경 감지 대신 서비스가 매번 `save` 를 불러야 하며, `@Version` 값을 도메인과 엔티티 사이로 옮겨야 한다
        + 모델과 테스트 대부분을 다시 쓰는 비용에 비해, 섹션 2 범위에서 얻는 것이 적다고 판단했다
    - 강의 예제 저장소도 도메인 모델에 JPA 를 둔다
+ 치르는 대가
    - 도메인 모델이 JPA 의 제약을 따른다 — `protected` 기본 생성자, JPA 가 관리하는 컬렉션, 지연 로딩
    - 영속성 기술을 바꾸거나 테이블 구조가 도메인 모델과 달라져야 하면 도메인 모델도 함께 바뀐다
+ 바꿔야 할 때
    - 섹션 3 에서 컨텍스트를 서비스로 떼어 내거나, 도메인 모델과 테이블 구조가 달라져야 할 때
    - 방법 — `adapter/out/persistence` 에 JPA 엔티티와 매퍼를 두고 도메인에서 애너테이션을 걷어낸다
    - 저장소가 이미 포트로 감춰져 있어 서비스는 저장 호출만 늘어나고 나머지는 그대로다

### 2. 에러 코드의 HTTP 상태 — 한계로 남김
+ 남은 것
    - 도메인 에러 코드 4개(`OrderErrorCode`, `ProductErrorCode`, `StockErrorCode`, `ReservationErrorCode`)가 `HttpStatus` 를 가진다
    - 공통 계약 `BaseErrorCode` 가 상태·메시지를 함께 요구하기 때문이다
+ 생긴 이유
    - 코드 하나에 상태와 메시지를 모아 두면, 예외를 응답으로 바꾸는 일이 `GlobalExceptionHandler` 한 곳에서 끝나 편하다
    - 대신 "이미 확정된 주문" 같은 도메인 규칙에 "HTTP 409"라는 웹 표현이 들어간다. 1번과 달리 의도한 선택은 아니었다
+ 치르는 대가
    - 도메인이 Spring Web 에 의존한다
    - 같은 규칙을 HTTP 가 아닌 곳(메시지, 섹션 4 의 gRPC)에서 쓸 때 상태 코드가 어색해진다
+ 고치는 법
    - 에러 코드는 종류(`NOT_FOUND` · `CONFLICT` · `INVALID`)만 갖고, HTTP 상태로 바꾸는 일은 웹 어댑터가 맡는다
    - API 응답은 그대로 유지된다
    - `common` 의 웹 코드(`GlobalExceptionHandler`, `ApiResponse`, `HealthController`)를 `adapter/in/web` 으로 옮기는 일과 함께 한다

### 3. application 의 스프링 의존 — 허용
+ `@Service`, `@Transactional`, `@Value`
    - 트랜잭션 경계는 유스케이스 단위라 application 이 갖는다
    - 미션이 말하는 "핵심 도메인"(domain)의 문제는 아니라고 본다
+ Lombok(`@Getter` 등)은 컴파일 시점 코드 생성이라 런타임 의존이 아니다

### 정리
|판단|대상|
|---|---|
|개선함|저장소·요청 DTO·다른 컨텍스트·연관 의존을 포트와 어댑터 뒤로|
|트레이드오프로 남김|도메인 모델의 JPA 애너테이션|
|한계로 남김 (고칠 방법 정리)|에러 코드의 HTTP 상태|
|허용|application 의 스프링, Lombok|
