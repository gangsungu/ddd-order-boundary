## 기능 별 책임을 분리

### 상품 컨텍스트
판매자가 등록한 상품 정보와 재고 수량을 관리한다

+ 소유 데이터
    - 상품
        + 상품명, 설명, 가격, 판매상태, 판매자 ID 등
    - 재고
        + 가용수량, 예약수량
+ 변경 이유
    - 상품 정보
        + 판매자의 상품 등록, 수정
        + 플랫폼의 검수, 노출 정책
    - 재고
        + 판매자의 입고 등록
        + 주문에 의한 자동 예약, 차감
+ 분리 가능성
    - 재고는 주문마다 변경되어 쓰기 경합이 발생하지만 상품 정보는 읽기 위주
    - 상품 정보는 사람만 변경하는 반면에 재고는 주문 시스템이 자동으로 변경
    - 현재 범위 내에서는 하나의 컨텍스트로 두되 재고 경합이 문제가 되면 분리할 수 있다
+ 재고 예약 모델
    - 예약 기록(어느 주문이, 얼마를, 언제까지 잡았는가)은 보상 트랜잭션을 되돌릴 근거로 존재한다
    - 주문 생성이 가용수량을 예약수량으로 옮기고, 결제 결과가 그 예약을 확정하거나 해제한다
        + 결제 성공 - 예약수량이 소멸하며 차감이 확정된다
        + 결제 실패, 예약 만료 - 가용수량으로 되돌아간다. 이것이 보상 트랜잭션이다
    - 예약 주체를 남기지 않고 재고에 예약수량 컬럼만 더하면 만료 해제와 부분 취소를 처리할 수 없다
    - 서비스가 분리되면 이 기록은 선택이 아니라 필수가 된다
        + 재고 서비스는 주문 테이블을 읽을 수 없으므로 예약 주체와 만료 시점을 자기 소유 데이터로 가져야 한다
        + 미확정 예약의 해제를 재고 서비스가 스스로 판단해야 한다
        + 하나의 데이터는 하나의 컨텍스트만 소유한다는 원칙의 귀결이다

|컨텍스트|변경 이유|수명 주기|트랜잭션 범위|
|---|---|---|---|
|주문|구매, 취소 정책|||
|상품|판매자의 상품 등록, 재고 입고, 플랫폼 검수 정책|주문과 무관|불필요 (재고 예약모델)|
|결제|PG사 스펙, 결제수단 추가 (외부)|주문보다 긴 트랜잭션 (응답을 주고받아야 하므로)|불가능 (외부 호출)|
|정산|수수료율, 정산주기|주문보다 길다|불필요|

주문은 확정되면 상태 변화가 끝나지만 정산은 주문이 끝난 시점부터 집계, 지급 단계를 거치며 계속 상태가 변화  
환불이 발생하면 이미 종료된 주문은 그대로지만 정산 금액은 환불액만큼 변화한다
